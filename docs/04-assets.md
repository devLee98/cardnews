# `back/assets.py` — 브랜드 상세 이미지를 골라내는 곳

> **한 줄 요약**
> 브랜드 상세페이지 사진을 실제로 내려받아서, 카드에 쓸 만한 것만 남깁니다.
> AI에게 물어보기 **전에** 기계적으로 걸러내는 1차 필터입니다.

---

## 1. 왜 필요한가요

브랜드 상세페이지 이미지 목록에는 여러 종류가 뒤섞여 있습니다.

| 종류 | 쓸 수 있나 |
|---|---|
| 실제 제품 연출컷 | ✅ 아주 좋음 |
| 후기 애니메이션 (움짤) | ✅ 좋음 |
| 사용 전후 비교 이미지 | ✅ 좋음 |
| 브랜드 로고만 있는 상단 배너 | ❌ |
| 글자가 가득한 설명 이미지 | ❌ |
| **860×1 짜리 여백 띠** | ❌ |

마지막 항목이 특히 골칫거리입니다. 상세페이지를 만들 때 여백을 주려고 넣은 **가로로 긴 실선 한 줄**인데, 이게 이미지 목록에 수십 개씩 들어 있습니다.

**주소만 봐서는 어느 쪽인지 구분이 안 됩니다.** `detail_07.jpg` 라는 이름만으로는 연출컷인지 여백 띠인지 알 수 없습니다.

그래서 **실제로 내려받아서 열어 봅니다.**

---

## 2. 2단계 필터

```
상세 이미지 수십 장
      ↓
  [1차] assets.py — 기계적 필터
      · 실제로 내려받아 크기를 잼
      · 너무 작거나 비율이 극단적인 것 제거
      · 내용이 같은 파일 제거 (이름만 다른 사본)
      ↓
  [2차] AI 비전 검수 (02-prompts.md ②번)
      · 무엇이 찍혀 있는지 눈으로 보고 판단
      ↓
  최종 후보
```

1차에서 걸러내는 이유는 **비용과 속도** 때문입니다. 여백 띠 50장을 AI에게 보여주는 건 낭비입니다.

---

## 3. 1차 필터 기준

### 어디서 사진을 찾나

```
events[].products[].detail_image_urls
```

**이 경로 하나만 봅니다.** 상품 대표 이미지(`image_url`)는 쓰지 않습니다.
대표 이미지는 상품마다 비슷한 정면 컷이라, 그것만 참고하면 카드가 전부 비슷해지기 때문입니다.

최대 300개까지 주소를 모읍니다.

### 중복 제거는 두 번 합니다

**1차 — 주소가 같으면 제거.** 여러 상품이 똑같은 주소를 쓰고 있으면 한 번만 남깁니다.

**2차 — 파일 내용이 같으면 제거.** 브랜드가 **같은 사진을 상품마다 다른 이름으로** 올리는 일이 흔합니다.

```
review_a.gif      ┐
review_01.gif     ├ 주소는 다르지만 내용은 같은 파일
x.gif?v=1         ┘
```

주소만 비교하면 이게 전부 다른 이미지로 취급돼서, **화면에 같은 후기 움짤이 여러 장 뜹니다.**
어차피 크기를 재려고 파일을 전부 내려받으니, 그때 파일 내용의 지문(해시)을 같이 계산해서 겹치는 것을 버립니다. 먼저 나온 쪽을 남깁니다.

> 💡 **완전히 같은 파일만 잡습니다.** 브랜드가 크기를 줄여 다시 저장한 사본은 파일 내용이 달라져서 걸러지지 않습니다.
> 그런 경우까지 잡으려면 사진을 눈으로 비교하는 방식(시각적 해시)이 필요한데, 비슷한 두 컷을 같은 것으로 착각할 위험이 있어 지금은 넣지 않았습니다.

### 크기 기준

| 기준 | 값 | 걸러내는 것 |
|---|---|---|
| **최소 변 길이** | 400px | 작은 아이콘, 얇은 여백 띠 |
| **가로세로 비율** | 0.35 ~ 2.5 | 세로로 아주 긴 설명 이미지, 가로로 아주 긴 배너 |

**비율 0.35 = 세로가 가로의 약 3배.** 이보다 길면 카드(4:5)로 잘라냈을 때 내용이 남지 않습니다.
**비율 2.5 = 가로가 세로의 2.5배.** 이보다 넓으면 대부분 상단 배너입니다.

### 움직이는 이미지인지 확인

파일을 열어서 프레임이 2개 이상이면 움짤로 판정합니다.
확장자가 `.gif`가 아니어도(움직이는 webp 등) 정확히 잡아냅니다.

## 4. AI에게 보낼 미리보기 만들기

원본 사진은 크기가 큽니다. 그대로 보내면 느리고 비쌉니다.
그래서 **512px로 줄인 JPEG 미리보기**를 만들어서 보냅니다.

- 긴 변 기준 512px로 축소
- JPEG 품질 70
- 움짤은 **첫 프레임만** 뽑아서 정지 이미지로

> 💡 AI가 알아야 할 건 "무엇이 찍혀 있는지"뿐이라 이 정도면 충분합니다.
> 작은 글씨까지 읽을 필요는 없습니다. (그래서 API 호출 시 "자세히 보기" 옵션도 끕니다)

## 5. 🔑 종류별로 나눠서 남기는 이유

이 부분이 실제 버그를 고치면서 생긴 로직입니다.

### 문제 상황

이미지는 JSON에 적힌 순서대로 나옵니다. 그 순서는 **상품 순서**입니다.

```
0~30번  : 첫 번째 상품(주방세제)의 상세 이미지
31~55번 : 두 번째 상품(핸드워시)의 상세 이미지
56~80번 : 세 번째 상품(욕조클리너)의 상세 이미지
```

여기서 "앞에서부터 20장만 남긴다"고 하면 어떻게 될까요?

**주방세제 이미지만 20장 남고, 핸드워시와 욕조클리너의 이미지는 통째로 사라집니다.**
특히 뒤쪽 상품의 좋은 움짤이 하나도 살아남지 못했습니다.

### 해결

**움직이는 것과 정지한 것을 따로 세어서, 종류별로 남깁니다.**

| 종류 | 남기는 수 | 왜 이만큼인지 |
|---|---|---|
| **움직이는 이미지** | 최대 20장 | 사용자가 화면에서 직접 눈으로 보고 고르는 목록이라, 선택지를 넉넉히 남깁니다 |
| **정지 이미지** | 최대 12장 | 참고용으로만 쓰이므로 이 정도면 충분합니다 |

> 💡 완벽한 해결은 아닙니다. 여전히 앞쪽 상품이 유리하지만, 움짤이 통째로 사라지는 문제는 없어졌습니다.

## 6. 다운로드 방식

- 모든 사진을 **동시에** 내려받습니다. 하나씩 받으면 수십 장에 몇 분이 걸립니다.
- 한 장당 20초를 기다리고, 실패하면 조용히 건너뜁니다. 한 장 때문에 전체가 멈추면 안 되기 때문입니다.

### ⚠️ Content-Type 헤더를 믿지 않습니다

정상적인 서버는 "이 파일은 이미지입니다"라는 헤더를 함께 보냅니다.
그런데 **일부 브랜드 상세페이지 서버는 이 헤더를 아예 안 보냅니다.**

헤더만 보고 걸렀더니 멀쩡한 webp 이미지들이 전부 버려지는 일이 있었습니다.
그래서 **헤더를 무시하고 실제로 파일을 열어 보고 판단합니다.**

## 7. `to_supported` — 이미지 형식 맞추기

이미지 편집 API는 세 가지 형식만 받습니다.

```
image/jpeg, image/png, image/webp
```

그런데 우리가 참고로 넣고 싶은 사진에는 gif와 움직이는 webp가 섞여 있습니다.
이건 **형식이 맞아도 거부됩니다** (움직이는 이미지라서).

그래서 이렇게 처리합니다.

| 상황 | 처리 |
|---|---|
| 정지 JPEG/PNG/WEBP | 그대로 사용 |
| gif | **첫 프레임만 뽑아 PNG로 변환** |
| 움직이는 webp | **첫 프레임만 뽑아 PNG로 변환** |
| 헤더가 없는 파일 | 열어 보고 판단, 필요하면 PNG로 변환 |
| 열리지 않는 파일 | 버림 |

> 💡 움짤을 첫 프레임으로 바꿔도 **참고 자료로서의 가치는 남습니다.** 제품 생김새와 색, 배경 분위기는 첫 프레임에도 그대로 있기 때문입니다.

## 8. 정지 이미지와 움짤은 쓰임새가 완전히 다릅니다

| | 정지 이미지 | 움직이는 이미지 |
|---|---|---|
| **누가 고르나** | AI가 자동으로 | **사용자가 화면에서 직접** |
| **AI 검수로 걸러지나** | ✅ 쓸 만하다고 본 것만 남음 | ❌ 안 걸러짐 (사람이 눈으로 보고 판단) |
| **어떻게 쓰이나** | 이미지 생성의 **참고 자료** | **원본을 그대로** 카드로 사용 |
| **문구** | 이미지 안에 함께 그려짐 | **없음** (원본에 글자를 그릴 수 없음) |
| **최대 사용 수** | 카드당 최대 5장 참고 | 전체 1장까지 |

**움짤을 AI 검수로 거르지 않는 이유**는, 어차피 사용자가 화면에서 눈으로 보고 고르기 때문입니다.
기계가 미리 걸러버리면 사용자가 선택할 기회조차 없어집니다.

**움짤 카드에만 문구가 없는 이유**는, 이미지 생성 AI가 움직이는 이미지를 만들지 못하기 때문입니다.
원본을 그대로 쓸 수밖에 없어서, 문구를 그 안에 그려 넣을 방법이 없습니다.
예전에는 이미지 아래에 문구 띠를 붙였지만 **내보내면 사라져서**, 지금은 아예 두지 않습니다.
(→ 10절, [05번 문서](05-controller.md))
그래서 다른 카드와 결이 달라지고, 최대 1장으로 제한합니다.

## 9. `pick_accent` — 제품 사진에서 포인트 색 뽑기

카드 문구는 원래 **흰색 아니면 먹색** 두 가지뿐이었습니다. `theme` 값이 그 둘만 갖고 있어서,
어떤 공구를 넣어도 글자 톤이 똑같았습니다.

그렇다고 AI에게 색을 고르라고 하면 **사진에 없는 색을 지어내** 제품과 겉돕니다.
공구 데이터에 브랜드 색이 있는 것도 아닙니다 (`brand.keyword`는 비어 있고 색 필드가 없습니다).

그래서 **브랜드가 직접 찍은 사진에서 색을 빌려 옵니다.** 사진에 실제로 있는 색이라
무엇이 뽑히든 제품과 어울립니다.

### 어떻게 뽑나요

1. 상품 **대표컷**(`image_url`) 5장을 받습니다
2. 각각 80×80으로 줄이고 픽셀을 HSV로 봅니다
3. **배경과 그림자를 버립니다** — 채도 0.25 미만, 명도 0.15 미만 또는 0.95 초과
4. 남은 픽셀의 색상(hue)을 24칸(한 칸 15°)에 나눠 담습니다
5. 가장 많이 담긴 칸의 평균 색상을 고릅니다
6. 색상만 쓰고 **진하기는 고정값으로 갈아끼웁니다**

> 🔑 **3번이 핵심입니다.** 제품컷은 대부분 흰 배경이라, 걸러내지 않으면 언제나 회색이 뽑힙니다.

> 🔑 **6번을 하는 이유.** 사진에서 나온 채도·명도를 그대로 쓰면 글자가 배경에 묻히거나
> 형광색이 됩니다. 색상만 가져오고 진하기는 글자가 읽히는 값으로 고정합니다.
> 밝은 바탕에는 깊게(`S 0.60 / V 0.50`), 어두운 바탕에는 밝게(`S 0.60 / V 0.88`) 씁니다.

### 왜 여러 장을 합치나요

한 장만 보면 **그 상품 포장 색이 공구 전체의 색**이 됩니다.
같은 공구 안에서도 상품마다 색이 달라서, 어느 장을 골랐느냐로 카드 색이 뒤바뀝니다.

```
프랭클린 대표컷 1장씩 따로 뽑으면   #805033(갈색)  #335180(파랑)
5장을 합치면                      #335180  ← 가장 넓게 쓰인 색
```

### 왜 상세컷이 아니라 대표컷인가요

상세컷(`detail_image_urls`)은 맨 앞 서너 장이 **흰 배너**인 경우가 많아 색이 안 나오고,
**30MB짜리**가 섞여 있어 색 하나 뽑자고 받기에는 무겁습니다.
대표컷은 수십 KB짜리 깔끔한 제품컷이라 모든 공구에서 색이 나왔습니다.

### 실제로 뽑힌 색

| 공구 | 밝은 바탕 | 어두운 바탕 |
|---|---|---|
| 강윤맘 X 로보카폴리 | `#80333C` | `#E05A6A` (폴리의 빨강) |
| 도하맘 X 어네이브 | `#33807B` | `#5AE0D9` (시카의 청록) |
| 씽맘 X 롤베이비 | `#805C33` | `#E0A35A` (러그의 베이지) |

색이라고 할 만한 픽셀이 2% 미만이면 **`None`을 돌려주고 포인트 색을 쓰지 않습니다.**
흑백에 가까운 사진에서 억지로 색을 뽑으면 엉뚱한 색이 나옵니다.

> 💡 **색은 `highlight` 한 곳에만 씁니다.** 제목과 본문은 지금처럼 흑/백입니다.
> 여러 곳에 뿌리면 색이 흔해져서 시선을 끄는 힘이 사라집니다.
> 계산은 공구당 한 번이고 결과를 캐시합니다. 카드는 한 장씩 따로 만들어지는데,
> 캐시가 없으면 같은 사진을 카드 수만큼 다시 받고 **카드마다 색이 달라질 수** 있습니다.

## 10. `fit_to_card` — 움짤을 카드 규격에 맞추기

움짤 카드는 AI 가 그리지 못해 **브랜드 원본을 그대로** 씁니다.
그래서 두 가지가 어긋나 있었습니다.

1. 글자를 이미지 안에 그려 넣을 수 없어, 화면에서만 아래에 문구 띠를 붙였습니다.
   → **내보내면 그 문구가 사라집니다.** DOM 에만 있던 글자라 파일에는 담기지 않습니다.
2. 원본은 비율이 제각각입니다. 실측 **0.62 ~ 2.13** 이었습니다.
   → 4:5 카드 아홉 장 사이에 혼자 다른 비율로 낍니다.

1번은 문구를 아예 없애서 해결했고(→ [05번 문서](05-controller.md)),
2번은 내보낼 때 이 함수가 4:5 로 맞춥니다.

### 자르지 않고 여백을 채웁니다

가로로 긴 원본을 4:5 로 **자르면 내용이 날아갑니다.**

```
860x403 을 4:5 로 자르면  →  322x403   폭의 63% 손실
860x403 에 여백을 채우면  →  860x1075  손실 없음
```

여백 색은 **원본 가장자리에서 가장 많은 색**을 씁니다.
상세컷은 배경이 흰색인 경우가 대부분이라, 검은 띠와 달리 이어 붙인 티가 나지 않습니다.

### GIF 는 팔레트를 공유시킵니다

RGB 로 그냥 저장하면 **프레임마다 팔레트가 따로 생겨 파일이 대여섯 배로 붑니다.**

```
106KB  →  596KB   프레임마다 팔레트
```

## 11. 이 파일을 고칠 일이 있다면

| 하고 싶은 것 | 고칠 곳 | 현재 값 |
